# P4 关键词与语义检索质量评估计划

## 一、目的与范围

本阶段回答的是：

> 对真实中英文文献问题，`GET /search` 关键词检索和 `POST /semantic-search` 语义检索分别能找到什么，
> 哪一路排名更合理，二者是否存在稳定互补？

本阶段只做评估，不实现混合检索、不修改现有排序算法，也不把大语言模型引入评分过程。

## 二、为什么先建测试集

如果没有固定问题和期望答案，每次人工尝试都会更换问题，很容易根据偶然结果得出结论。固定测试集
可以让后续索引、模型、分块和排序调整使用同一把尺子，并留下可重复的证据。

## 三、测试数据前提

进入正式对比前需要确认：

1. 至少有一份中文文献和一份英文文献处于 `ready`；
2. 两份文献都有完整 `text_chunks`；
3. 两份文献都使用当前 `model_name + dimensions` 生成了完整向量；
4. 测试者能够根据原文提前标注至少一个期望文档、文本块或物理页码；
5. 测试期间不切换 Embedding 模型，不重新切分文本。

## 四、第一版问题组成

第一版建议不少于 10 个真实问题，中英文均不少于 4 个，并覆盖：

| 类型 | 目的 |
|---|---|
| 原文术语问题 | 验证关键词检索的基本优势 |
| 同义改写问题 | 验证不包含原文字面词时的语义召回 |
| 机制或因果问题 | 验证语义是否能找到解释性段落 |
| 具体方法问题 | 验证模型名、控制方法、实验方法等细节 |
| 跨语言问题（可选） | 验证中文问英文文献或英文问中文文献的能力 |

问题必须来自真实阅读需求。不能先看检索结果再反向编造一个一定能命中的问题。

## 五、单条测试用例结构

每条测试用例至少记录：

```text
case_id               稳定编号
language              问题语言：zh / en
natural_question      用户真实会提出的完整问题
keyword_query         为关键词接口准备的核心字面词或短语
expected_document_id  预期文献，可为多个
expected_pages        已知时记录物理页码
expected_concepts     预期答案应涉及的概念
reason                为什么认为这些来源相关
```

`natural_question` 交给语义检索；`keyword_query` 交给关键词检索。两者表达同一个信息需求，但不能为了
让某一路获胜而选择明显不合理的词。

## 六、执行方式

每条问题固定比较前 5 条结果：

```text
GET  /search?q=<keyword_query>&page=1&page_size=5
POST /semantic-search
{
  "query": "<natural_question>",
  "top_k": 5
}
```

如果测试目标是单篇文献，两路请求都提供相同 `document_id`；如果测试全库发现能力，两路都不提供
文档过滤。不能一边限定文档、另一边全库检索。

## 七、结果记录

每个返回结果记录：

```text
retrieval_type    keyword / semantic
rank              1～5
document_id
chunk_id
page_start/page_end
score             语义相似度；关键词第一版没有相关性分数则留空
relevance         0 / 1 / 2
comment           判断依据
latency_ms
```

人工相关性采用三级：

- `2`：直接回答问题或提供关键证据；
- `1`：主题相关，但不能直接回答；
- `0`：与问题无关。

评分时优先阅读完整 chunk 和相邻来源，不只根据标题或相似度数字判断。

## 八、第一版指标

第一版使用容易解释的指标，不提前引入复杂评估框架：

- `Hit@5`：前 5 条是否至少包含一条直接相关结果；
- `First Relevant Rank`：第一条相关结果排在第几位；
- `Top-5 Relevance Sum`：前 5 条人工相关性分数总和；
- `Expected Source Hit`：是否命中预先标注的文档或页码；
- `Latency`：端到端响应时间；
- `Unique Relevant Hits`：某一路独有、另一条路线前 5 中没有的相关结果。

## 九、公平性约束

- 使用同一批 `ready` 文档；
- 两路使用相同文档过滤范围和返回数量；
- 在运行前冻结问题、关键词和期望来源；
- 不因为一次结果不好而临时修改某一路输入；
- 报告空结果、失败请求和远程服务异常，不只保存成功案例；
- 关键词检索和语义检索的分数含义不同，不能直接相加或比较绝对大小。

## 十、混合检索的重新评估条件

混合检索当前不开发。只有同时满足以下条件时才重新讨论：

1. 测试集规模和中英文覆盖达到本计划最低要求；
2. 关键词检索在原文术语问题上稳定优于语义检索；
3. 语义检索在同义改写或自然语言问题上稳定找到了关键词遗漏的相关结果；
4. 两路存在可重复的 `Unique Relevant Hits`，而不是单个偶然案例；
5. 产品场景确实需要在一个结果列表中同时利用两路优势。

即使满足条件，也要先设计：候选集合大小、去重键、分数归一化、融合排序、分页语义、响应 DTO 和
降级规则，再决定是否编码。若证据显示独立的两个接口已经足够，就继续保持独立，不为架构完整感
增加复杂度。

## 十一、下一步执行顺序

1. 盘点当前中文和英文 `ready` 文献及其向量完整性；
2. 由学习者先提出真实问题和期望来源；
3. 冻结第一版测试用例；
4. 编写可重复运行但不会修改业务数据的评估脚本；
5. 运行两路检索并保存原始结果；
6. 人工完成 0/1/2 相关性标注；
7. 汇总指标和失败案例；
8. 输出评估结论；
9. 混合检索继续保留在后续路线，不在当前阶段直接实现。
