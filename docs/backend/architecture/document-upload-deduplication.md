# 文档上传内容去重设计

> 状态：第一版已实现；更新时间：2026-08-18。

## 1. 核心目的

同一用户可能用不同文件名重复上传内容完全相同的文献。如果每次都创建新文档，就会重复占用文件、
解析、文本块和向量资源，也会让搜索结果出现重复来源。第一版只在同一用户内部去重，不跨用户共享
物理文件，从而保持权限、删除和生命周期边界简单。

## 2. 分层职责

```text
HTTP Handler
  → 流式读取 multipart，映射 200/201 和 duplicate 字段
Application UploadService
  → 保存文件，调用原子创建/查重，编排补偿删除
Domain Repository Contract
  → 描述 CreateOrGetBySHA256 的稳定输入输出
PostgreSQL Repository
  → INSERT ... ON CONFLICT，读取已有文档
Database Migration
  → UNIQUE(owner_user_id, sha256) 解决并发竞争
LocalStorage
  → 流式写盘并计算可信 SHA-256，不负责业务查重
```

Handler 不查询数据库，LocalStorage 也不知道用户和文档表。是否重复属于上传用例的业务流程，因此由
Application 编排；并发唯一性必须由 PostgreSQL 约束保证。

## 3. 处理顺序

1. LocalStorage 流式保存上传内容，同时计算实际大小、MIME 和 SHA-256；
2. Repository 尝试按当前 `OwnerScope` 和元数据插入文档；
3. 插入成功：保留新文件，返回 `Created=true`；
4. `(owner_user_id, sha256)` 冲突：查询并返回原记录，Application 删除本次新文件；
5. 数据库失败：Application 删除本次新文件并返回错误；
6. 补偿删除使用脱离 HTTP 取消信号的 5 秒有界上下文，避免客户端断开后立刻放弃清理；
7. 补偿删除也失败：同时保留原始错误或明确返回清理错误，不能静默遗留孤立文件。

必须先完整读取文件才能得到可信 SHA-256，因此第一版会短暂写入一个新文件，再在命中重复时删除。
这比信任浏览器提交的哈希安全，也始终保持固定内存使用。

## 4. HTTP 契约

- 首次上传：`201 Created`，响应文档中包含 `"duplicate": false`；
- 同一用户重复内容：`200 OK`，返回第一次上传的文档并包含 `"duplicate": true`；
- 不同用户的相同内容：各自得到 `201` 和独立记录；
- 文件名不参与查重。重复上传使用新文件名时，返回的 `original_name` 仍是第一次上传的名称；
- 重复不是异常，不返回 `409`。`409` 更适合“请求与资源当前状态冲突且操作没有得到可用结果”的场景。

## 5. 并发与一致性

只写“先 SELECT、没有再 INSERT”存在竞态：两个请求可能同时看到不存在并都插入。当前使用数据库唯一
索引作为最终裁判，`INSERT ... ON CONFLICT DO NOTHING` 的落败请求读取胜出记录。仓储还对“冲突记录
恰好被并发删除”的极小窗口执行有界重试。

数据库与本地文件系统无法加入同一个 PostgreSQL 事务，所以这里使用补偿操作，而不是假装拥有跨系统
原子事务。测试分别验证数据库错误清理、重复文件清理、并发只创建一条记录，以及真实 HTTP 后只留下
一条记录和一个物理文件。

## 6. 后续边界

当前不做模糊重复、相似文献判断、跨用户 Blob 共享、引用计数或管理员全局去重。这些能力会显著增加
隐私、删除语义和事务复杂度。若未来文件规模增长，可另建内容寻址 Blob 表和引用关系，不需要改变
前端现有的 `duplicate` 语义。
