# 概念词典、多语言标注与语义检索设想

> 状态：已记录，尚未实现。当前 P3 仍以可测量的关键词检索为主线。

## 目的

未来允许系统建立稳定的专业概念，把同义词、中英文表达和文本块来源关联起来，
从而支持多概念组合检索和跨语言检索，后续再扩展到向量语义检索。

## 概念数据模型候选

```text
concepts
└─ 稳定概念，例如“磁浮列车”

concept_aliases
├─ 磁浮列车
├─ 磁悬浮列车
├─ maglev train
└─ magnetic levitation train

chunk_concepts
└─ chunk_id + concept_id + source + confidence
```

文档级概念第一版可以通过 `chunk -> document` 联表汇总，不必同时复制一份
`document_concepts`，避免两套派生数据不一致。

## 预期处理流程

```text
文档解析并生成 chunks
→ 使用带版本的概念词典分析 chunk
→ 保存 chunk 与 concept 的派生关联
→ 用户查询先解析为稳定 concept_id
→ 按 AND / OR 及来源文档规则检索
```

已知同义词和中英文别名由概念词典解决；未知但语义接近的表达属于 P4 向量
检索。两者不在第一版中混成一个不可解释的搜索规则。

## 与缓存的边界

- `chunk_concepts` 是可重建但需要持久化的派生标注，不是缓存；
- PostgreSQL 索引负责根据 `concept_id`、`chunk_id` 等条件快速定位数据；
- 查询结果、概念词典或 Embedding 缓存只在实际测量证明存在重复计算瓶颈后增加；
- 文档上传、重新解析、删除或词典更新都会影响缓存失效，因此当前不提前
  引入 Redis 或大规模内存缓存。

## 分阶段路线

1. **P3**：完成字面关键词检索、过滤、确定性排序和性能基线；
2. **P3.5 候选**：引入概念词典、同义词、中英文别名和 chunk 概念标注；
3. **P4**：引入 Embedding、语义相似度、多路检索融合和带来源引用的问答；
4. **性能证据出现后**：再设计概念词典、查询结果或 Embedding 缓存与失效机制。

## 重启该设计前必须确认

- 多概念查询默认采用 AND 还是 OR；
- 概念必须出现在同一 chunk，还是同一文档即可；
- 概念词典由用户维护、系统推荐，还是两者结合；
- 派生标注如何记录词典/模型版本并支持重建；
- 用户手工标注与自动标注的优先级和冲突处理。
