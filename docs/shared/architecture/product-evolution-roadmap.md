# 产品演进路线：个人版、工程化前端与未来多用户

## 1. 当前定位

项目当前是面向个人、本机或受信网络使用的单工作区文档知识平台。后端 P0～P4 第一版已经形成
“上传 → 解析 → 分块 → 检索 → 向量 → 带来源问答”的完整链路；前端仍处于 F0 工程骨架阶段。

当前没有用户、登录、工作区、成员关系或租户隔离。所有文档、任务、文本块、向量和问答能力属于同一个
隐含的个人工作区。因此当前服务不能直接作为公开互联网的多人 SaaS 部署。

## 2. 三条独立但协同的路线

```text
后端能力路线 P0～P4（第一版已完成）
        ↓
后端 P5 工程化 ───────────────┐
                               ├─ 个人版产品闭环
前端 F0～F5 ──────────────────┘
        ↓
满足真实多人需求后进入 P6
        ↓
用户、工作区、权限与多租户
```

三条路线不能混用同一阶段名称：

- `P5` 专指现有 Go/Python/PostgreSQL 后端的工程化；
- `F0～F5` 专指 Vue 前端从工程骨架到部署；
- `P6` 专指未来用户、工作区和多租户产品化。

## 3. 后端 P5：个人版工程化

P5 不新增复杂业务能力，目标是把当前可运行后端变成可重复构建、可部署、可观察和可恢复的个人版服务。

### P5.1 运行路径与配置

- 统一 Python 源码、文件存储、迁移和其他资源路径的解析基准；
- 消除“必须从 `backend` 目录启动”的隐含条件；
- 区分开发、测试和部署配置，启动时完成明确校验；
- 保证密钥不进入 Git、日志和前端产物。

2026-08-15 第一版实现采用统一 `APP_ROOT`：开发环境省略该配置时，从当前目录向上发现项目根；
部署环境显式配置时只接受已经存在的绝对目录。`STORAGE_ROOT` 与 `PYTHON_SOURCE_ROOT` 的相对值
统一基于 `APP_ROOT` 解析，迁移 SQL 继续通过 `go:embed` 随后端编译，不受运行目录影响。

### P5.2 日志与可观测性

- 增加请求 ID 和结构化日志；
- 区分用户安全错误、内部诊断错误和外部供应商错误；
- 记录任务 ID、文档 ID、处理阶段、耗时和最终状态；
- 建立 Embedding、Generation 的延迟、Token、重试和失败分类基线。

2026-08-15 已完成第一小步：所有 Gin 路由都通过 `X-Request-ID` 中间件和 JSON 访问日志中间件；
请求 ID 会进入响应头与标准 `context.Context`，访问日志按 `INFO/WARN/ERROR` 区分最终 HTTP 状态。
第二小步第一版已在文档查询与解析任务查询中建立安全响应和内部诊断双通道：调用方收到稳定错误码，
未知原始错误仅进入带请求 ID、诊断码和业务 ID 的后端日志。第三小步已为文档解析 Worker 建立
`started`、`succeeded`、`failed` 和 `unfinished` 生命周期事件。第四小步已覆盖 Embedding 任务的成功、重试、
永久失败、停机中断和未完成状态，并记录远程调用次数、延迟、Token 与供应商错误分类。下一步继续 Generation 指标。

### P5.3 构建、部署与数据维护

- 固化 Go、Python、Vue 与 PostgreSQL 的本地构建和启动流程；
- 提供 Docker/Compose 部署与健康检查说明；
- 明确数据库迁移、备份、恢复和本地文件备份流程；
- 验证优雅关闭和异常重启后的任务恢复。

### P5.4 自动化回归

- 固化 Go、Python 和前端测试命令；
- 建立不消耗远程费用的默认回归套件；
- 把真实数据库、真实 PDF 和远程模型验收作为显式可选测试；
- 在提交或发布前执行格式、静态检查、构建和契约检查。

### P5.5 完成标准

- 可以从文档指定的任意目录稳定启动，而不依赖偶然的当前工作目录；
- 新环境能够按说明完成配置、迁移、启动、健康检查和备份恢复；
- 关键请求和后台任务能够通过日志定位；
- 默认回归不需要真实密钥且结果可重复；
- 当前个人版能力边界、安全边界和资源消耗有正式记录。

## 4. 前端 F0～F5：个人版产品交互

- `F0` 工程骨架：目录、路由、状态、HTTP、组件库、测试和规范；
- `F1` API 基础：统一 Client、环境配置、错误模型、健康检查；
- `F2` 文档管理：上传、列表、详情、删除、解析与向量任务状态；
- `F3` 检索工作台：关键词检索、分页、文档过滤、来源和文本块查看；
- `F4` AI 工作台：语义检索、带来源问答、语言选择、超时与费用提示；
- `F5` 前端工程化：端到端测试、可访问性、性能、构建与部署。

前端第一版仍只有一个隐含的本地用户，不开发登录页、成员管理和租户切换。未来 P6 引入身份后，前端再
增加认证状态、工作区选择器、权限态和登录过期处理。

## 5. P6：用户、工作区与多租户

P6 是跨前端、后端、数据库和文件存储的独立阶段，不属于 P5 的顺手增强。

### 5.1 进入 P6 的前置条件

至少满足以下一项真实需求后再启动：

- 需要部署给两个及以上互不信任的用户；
- 用户需要拥有独立文献库；
- 需要团队共享文献并区分管理员与成员；
- 需要按用户或团队限制存储、任务和模型费用；
- 需要审计谁上传、删除、处理或查询了哪些资源。

### 5.2 核心名词

- `User`：可以登录的自然人或服务身份；
- `Workspace`：文档与 AI 能力的数据隔离边界，对用户比 `Tenant` 更直观；
- `Membership`：用户与工作区之间的成员关系及角色；
- `Actor`：一次请求中已经通过认证的调用者；
- `Role/Permission`：成员可以执行的操作范围。

第一版多用户模型优先使用 `Workspace` 作为产品名词；`tenant` 只作为架构层的隔离概念，不直接暴露给
普通用户。

### 5.3 分步实施

#### P6.0 身份与隔离设计

- 明确个人账户、团队工作区和成员角色；
- 选择 Session/Cookie 或 Token 认证方式；
- 设计越权威胁模型、密码/第三方登录策略和数据迁移方案；
- 冻结 API 兼容策略后再修改数据库。

#### P6.1 用户认证

- 建立 `users` 和认证凭据/会话模型；
- 实现注册、登录、退出、身份查询和认证中间件；
- Handler 从可信认证上下文取得 Actor，不能相信前端直接提交的 `user_id`。

#### P6.2 工作区与数据归属

- 建立 `workspaces`、`workspace_memberships`；
- 文档增加 `workspace_id`，派生的任务、chunks 和向量通过文档归属形成一致边界；
- 文件存储路径加入不可猜测的工作区隔离段；
- 迁移现有个人数据到一个默认个人工作区。

#### P6.3 授权与全链路隔离

- Application 对读取、上传、删除、处理、向量化、检索和问答执行权限规则；
- Repository 的查询必须带工作区范围，不能查询后再在 Handler 过滤；
- 关键词、语义检索和问答只使用当前工作区证据；
- 增加跨工作区 ID 猜测、搜索泄漏和任务越权测试。

#### P6.4 配额、审计与运营

- 按工作区限制文件大小、总存储、并发任务和远程 Token；
- 记录上传、删除、重新处理、向量化和高成本问答等审计事件；
- 根据真实负载再讨论多 Worker、队列、缓存、限流和计费。

### 5.4 P6 对现有模块的影响

| 模块 | 未来变化 |
|---|---|
| API/Handler | 读取认证 Actor，不接受客户端伪造用户归属 |
| Application | 把工作区权限和资源归属纳入用例规则 |
| Domain | 增加 User、Workspace、Membership 等稳定业务名词 |
| Repository | 所有文档、任务与检索操作带工作区范围 |
| PostgreSQL | 新增身份/成员表及文档工作区外键和隔离索引 |
| 文件存储 | 按工作区隔离物理路径并防止跨目录访问 |
| Worker | 任务携带并验证文档所属工作区，不改变解析器核心职责 |
| Embedding/RAG | 模型配置、配额和检索证据受工作区边界约束 |
| 前端 | 增加登录、工作区切换、成员与权限状态 |

## 6. 现在为未来保留什么，不提前实现什么

现在继续保持 Handler → Application → Domain → Infrastructure 的依赖边界，并让数据库访问集中在
Repository 中。这些边界能降低 P6 改造成本。

当前不提前增加永远写死为同一个值的 `tenant_id`，也不创建没有认证来源的“伪用户”。没有真实身份和
权限规则时，这些字段只能制造安全错觉与迁移负担。P6 启动时应使用正式迁移把现有数据归入默认个人
工作区，并为每条查询增加可测试的隔离条件。

## 7. 推荐执行顺序

```text
当前优先：后端 P5.1 + 前端 F0/F1
       ↓
前端 F2：形成文档管理闭环
       ↓
前端 F3/F4：接入检索与问答
       ↓
后端 P5 其余工程化 + 前端 F5
       ↓
个人版部署与真实使用反馈
       ↓
出现明确多人需求后启动 P6
```

该顺序优先让已有后端能力真正可使用，同时不把未来 SaaS 复杂度提前压到个人版开发中。
