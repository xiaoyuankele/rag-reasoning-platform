# 产品演进路线：工程化基线、个人用户与未来团队协作

## 1. 当前定位

项目当前是面向个人、本机或受信网络使用的单工作区文档知识平台。后端 P0～P5 已经形成
“上传 → 解析 → 分块 → 检索 → 向量 → 带来源问答 → 工程化交付”的完整基线；前端 F0、F1 和
F3 关键词检索最小切片已经完成，F2 文档管理仍待实现。

当前代码已经实现个人用户、登录和 Session，并完成文档、解析任务、chunks、向量任务、关键词检索、
语义检索与问答的所有者隔离。历史无归属数据已经通过受控命令显式认领，`owner_user_id` 也已收紧为 `NOT NULL`；
后端个人用户数据边界已通过发布验收。P6 先支持多个独立个人账户及私有数据，团队工作区、
成员关系和权限延后到 P7。

## 2. 三条独立但协同的路线

```text
后端 P0～P5（已完成）
        ↓
P6 个人用户域：身份、Session、文档归属、全链路隔离
        ├─────────────────────┐
        ↓                     ↓
后端认证与隔离             前端登录态 + F2～F5
        └──────────┬──────────┘
                   ↓
          多个个人用户安全闭环
                   ↓
出现团队共享需求后进入 P7
                   ↓
工作区、成员、角色与租户配额
```

三条路线不能混用同一阶段名称：

- `P5` 专指现有 Go/Python/PostgreSQL 后端的工程化；
- `F0～F5` 专指 Vue 前端从工程骨架到部署；
- `P6` 专指个人账户、Session 和私有数据隔离；
- `P7` 专指未来团队工作区、成员权限和真正的多租户协作。

## 3. 后端 P5：个人版工程化

P5 不新增复杂业务能力，目标是把当前可运行后端变成可重复构建、可部署、可观察和可恢复的个人版服务。

### P5.1 运行路径与配置

- 统一 Python 源码、文件存储、迁移和其他资源路径的解析基准；
- 消除“必须从 `backend` 目录启动”的隐含条件；
- 区分开发、测试和部署配置，启动时完成明确校验；
- 保证密钥不进入 Git、日志和前端产物。

2026-08-15 第一版实现采用统一 `APP_ROOT`：开发环境省略该配置时，从当前目录向上发现项目根；
部署环境显式配置时只接受已经存在的绝对目录。`STORAGE_ROOT` 与 `PYTHON_SOURCE_ROOT` 的相对值
统一基于 `APP_ROOT` 解析，迁移 SQL 继续通过 `go:embed` 随后端编译，不受运行目录影响。

### P5.2 日志与可观测性

- 增加请求 ID 和结构化日志；
- 区分用户安全错误、内部诊断错误和外部供应商错误；
- 记录任务 ID、文档 ID、处理阶段、耗时和最终状态；
- 建立 Embedding、Generation 的延迟、Token、重试和失败分类基线。

2026-08-15 已完成第一小步：所有 Gin 路由都通过 `X-Request-ID` 中间件和 JSON 访问日志中间件；
请求 ID 会进入响应头与标准 `context.Context`，访问日志按 `INFO/WARN/ERROR` 区分最终 HTTP 状态。
第二小步第一版已在文档查询与解析任务查询中建立安全响应和内部诊断双通道：调用方收到稳定错误码，
未知原始错误仅进入带请求 ID、诊断码和业务 ID 的后端日志。第三小步已为文档解析 Worker 建立
`started`、`succeeded`、`failed` 和 `unfinished` 生命周期事件。第四小步已覆盖 Embedding 任务的成功、重试、
永久失败、停机中断和未完成状态，并记录远程调用次数、延迟、Token 与供应商错误分类。第五小步已覆盖在线
Generation 调用的开始、成功、失败和无证据跳过状态，通过请求 ID 关联访问日志，并记录远程延迟、Token、
证据数量和供应商错误分类。第六小步第一部分已提供零远程费用的 JSONL 成本汇总命令，能够统一统计调用次数、
Token 和平均/P50/P95 耗时。第七小步已增加可校验的日志级别与 JSON/Text 格式配置，并在正式 Logger 创建前
安全处理配置错误。下一步在明确授权后执行真实批次，并进入构建部署与数据维护。

### P5.3 构建、部署与数据维护

- 固化 Go、Python、Vue 与 PostgreSQL 的本地构建和启动流程；
- 提供 Docker/Compose 部署与健康检查说明；
- 明确数据库迁移、备份、恢复和本地文件备份流程；
- 验证优雅关闭和异常重启后的任务恢复。

2026-08-15 已完成 P5.3.1 后端容器化：多阶段镜像在编译阶段构建 Go 二进制，运行阶段固定使用
Python 3.11.16，并安装 `rag_ai` 与 PDF 依赖；最终进程以非 root 用户运行。Compose 已组合后端与
现有 pgvector PostgreSQL，后端等待数据库健康后启动，默认关闭远程 Embedding、语义检索和问答，
并通过容器健康状态、真实 `GET /health` 与 Python 模块导入验收。

P5.3.2 已建立 PostgreSQL custom dump、`storage/` tar、SHA-256 manifest 组成的配套备份，并提供默认
拒绝覆盖已有数据库和目录的恢复脚本。当前 46 篇文档、2729 chunks、460 vectors、45 个文件和
185,226,802 字节已完成真实隔离恢复，数据库五张核心表行数、文件数和字节数全部一致。

P5.3.3 已固定容器 `SIGTERM`、init 进程和 30 秒停止宽限期。真实验收中正常停止以退出码 0 在 443 ms
完成，强制 `SIGKILL` 以退出码 137 结束；重启后文档处理任务进入 `failed`，Embedding 任务回到 `queued`，
恢复事件、临时数据清理和零远程费用边界均已验证。下一步进入 P5.4 默认自动化回归。

### P5.4 自动化回归

- 固化 Go、Python 测试命令；前端测试归属独立 F5，不在后端分支修改前端源码；
- 建立不消耗远程费用的默认回归套件；
- 把真实数据库、真实 PDF 和远程模型验收作为显式可选测试；
- 在提交或发布前执行格式、静态检查、构建和契约检查。

P5.4.1 已建立 `run-backend-regression.ps1`：默认隔离数据库、Go/Python 进程集成和三个远程 AI 开关，依次
运行只读 Go 格式检查、无缓存 Go 测试、`go vet`、Python 39 项测试和 Compose 解析。首次故意在外层设置
危险开关后仍全部通过，总耗时 8663 ms，没有启动容器、访问 PostgreSQL 或调用远程模型。

P5.4.2 已建立显式本地集成套件：脚本创建一次性 `rag_integration_*` 数据库，顺序验证 migrations、真实
Repository、Document Worker、Go/Python 子进程和 HTTP/PDF/chunks/PostgreSQL 纵向链路，最后强制删除并
查询确认测试数据库不存在。成功路径五段全部通过；故意触发 Go/Python 失败后清理仍然通过。正式库五张核心表
行数前后完全一致，远程调用为零。

P5.4.3 已建立发布候选聚合入口与 L0～L4 验收矩阵。聚合脚本默认顺序执行 P5.4.1 与 P5.4.2；容器生命周期
通过显式参数加入，真实复杂 PDF 和远程供应商保持人工选样及单独授权。首次聚合验收耗时 21,977 ms，两个阶段
全部通过，正式库行数不变、临时数据库无残留、远程调用为零。P5.4 至此完成。

### P5.5 完成标准（2026-08-15 已满足）

- 可以从文档指定的任意目录稳定启动，而不依赖偶然的当前工作目录；
- 新环境能够按说明完成配置、迁移、启动、健康检查和备份恢复；
- 关键请求和后台任务能够通过日志定位；
- 默认回归不需要真实密钥且结果可重复；
- 当前个人版能力边界、安全边界和资源消耗有正式记录。

以上五项均已有对应实现、文档和真实验收证据。P5 完成指个人版工程化基线稳定，不代表已经实现 P6 的身份与
个人数据隔离，更不代表已经实现 P7 的工作区和租户能力；复杂 PDF/OCR 质量增量也不属于工程化完成条件。

## 4. 前端 F0～F5：个人版产品交互

- `F0` 工程骨架：目录、路由、状态、HTTP、组件库、测试和规范；
- `F1` API 基础：统一 Client、环境配置、错误模型、健康检查；
- `F2` 文档管理：上传、列表、详情、删除、解析与向量任务状态；
- `F3` 检索工作台：关键词检索、分页、文档过滤、来源和文本块查看；
- `F4` AI 工作台：语义检索、带来源问答、语言选择、超时与费用提示；
- `F5` 前端工程化：端到端测试、可访问性、性能、构建与部署。

原 F0～F5 路线建立在隐含本地用户上。P6 启动后，前端在继续 F2 文档管理前先接入登录、刷新恢复、
登录过期和受保护路由；工作区选择器、成员管理和角色界面仍留在 P7。

## 5. P6：个人用户与私有数据

P6 是跨前端、后端和数据库的独立阶段。它不把团队租户复杂度提前带入个人账户，但必须一次性覆盖
文档、任务、chunks、向量、检索和问答的完整数据边界。

详细设计、细化主线图、认证契约、历史数据迁移和验收矩阵见
[P6 个人用户域与私有数据闭环](personal-user-domain.md)。

### 5.1 已确认范围

- 新增个人 `User` 和 PostgreSQL 持久 Session；
- 使用 `HttpOnly` Cookie，后端从认证上下文恢复可信 Actor；
- `documents.owner_user_id` 成为个人数据归属根；
- 所有文档、任务、检索和问答查询在 Repository/SQL 阶段限定当前用户；
- 历史无归属数据经过显式认领后再设置 `NOT NULL`；
- 前端提供登录、注册、刷新恢复、退出和 401 处理；
- 两个互不信任用户之间通过自动化测试证明无 ID 和检索泄漏。

### 5.2 分步实施

#### P6.0 设计与交接（文档已完成）

- 冻结个人账户范围，不引入 Workspace、角色或 Redis；
- 冻结 Session Cookie、Actor、OwnerScope 和错误码方向；
- 完成前后端主线图、数据库分阶段迁移与越权测试矩阵；
- 后端实施清单见
  [P6 个人用户域后端交接](../../backend/architecture/personal-user-backend-handoff.md)。

#### P6.1 身份与 Session

> 当前进度：B1 用户、Session、验证码挑战的数据模型与迁移已完成；B2 密码规则、Argon2id、验证码生成与
> HMAC、Fake Sender、请求验证码用例及并发安全仓储已完成。B3 已交付验证码申请、注册、登录、
> 密码重置、Session 鉴权中间件、当前用户与幂等退出。B4 已完成核心文档接口的第一条所有者隔离纵向链路。

- 建立 `users`、`user_sessions`、`verification_challenges`、密码哈希和随机 Session Token；
- 以统一验证码挑战支持已验证邮箱或手机号注册；默认 Fake Sender 零费用，真实短信按需后置；
- 实现验证码、注册、登录、密码重置、退出、当前用户和认证中间件；
- Handler 从可信 Actor 取身份，不接受前端提交的 `user_id`；
- 验证码发送、登录、注册增加单实例限流和 Cookie 请求 Origin 校验。

#### P6.2 文档归属与基础隔离

> 当前进度：已完成。上传、列表、详情、删除、解析任务创建、processing job 查询和 chunks 浏览均在
> Handler、Application 与 Repository/SQL 全链路显式传递 Scope，并通过双用户真实 HTTP/PostgreSQL
> 隔离测试；Worker 保持系统级执行者。下一步进入 P6.3/B5。

- 文档增加 `owner_user_id`；
- 上传、列表、详情、删除、解析、chunks 和两类任务查询全部按 owner 限定；
- Worker 保持系统级领取，但结果只能写回任务所属文档；
- 使用受控命令显式认领历史数据。

#### P6.3 检索与问答隔离

> 当前进度：已完成。B5.1 隔离向量任务创建和查询，B5.2 隔离关键词检索，B5.3～B5.4 隔离语义检索与
> 问答证据链；Worker 保持系统级领取。B6 已完成历史数据显式认领，B7 已完成非空约束和发布验收。

- 关键词 count/data SQL 都加入 owner 条件；
- 语义就绪检查、向量相似度查询和可选文档过滤都加入 owner 条件；
- Answer 只使用已经隔离的语义证据；
- 不允许全局查询后再在 Handler 或 Go 内存中删除其他用户结果。

#### P6.3.1 历史数据显式认领

> 当前进度：B6 已完成。一次性命令默认只预览目标用户与无主文档数量；确认执行必须同时提供
> `-confirm` 和 dry-run 得到的 `-expected-unowned`。PostgreSQL 在同一事务中锁定写入、再次核对数量并
> 更新所有空归属文档，任何不一致都会回滚。当前 46 篇历史文档已认领，无主数量为 0。

#### P6.4 前端与发布验收

- 后端 Release B 已完成 `owner_user_id NOT NULL`、无作用域写入口清理和双用户发布验收；
- 建立 Auth Store、登录/注册页、受保护路由和 401 恢复；
- 完成登录后上传、任务状态、搜索、问答和删除闭环；
- 通过双用户 ID 猜测、任务越权、关键词泄漏和语义来源泄漏测试；
- 前端不提交 `user_id`，通过浏览器 Cookie 使用后端已验证的 Session。

### 5.3 P6 完成标准

- 用户刷新页面后可以通过 `/users/me` 恢复身份；
- 用户只能管理和检索自己的文档；
- 密码、Cookie、Session Token 和文档正文不进入日志；
- 当前全部业务接口已明确公开或受保护边界；
- 默认回归仍不产生远程模型费用；
- 服务才可以交给多个互不信任的个人用户使用。

## 6. P7：团队工作区与多租户

P7 只有出现团队共享知识库的真实需求后再启动，计划能力包括：

- `Workspace`：文档与 AI 能力的数据隔离边界，对用户比 `Tenant` 更直观；
- `Membership`：用户与工作区之间的成员关系及角色；
- `Role/Permission`：成员可以执行的操作范围。

P7 再把 P6 的 `OwnerScope` 演进为 `WorkspaceScope`，增加共享、配额、审计和工作区物理存储边界。

## 7. 现在为未来保留什么，不提前实现什么

现在继续保持 Handler → Application → Domain → Infrastructure 的依赖边界，并让数据库访问集中在
Repository 中。这些边界能降低 P6/P7 改造成本。

P6 不提前增加永远写死为同一个值的 `tenant_id`，也不创建固定密码或自动归属的“伪用户”。历史文档由
真实账户显式认领；P7 再通过正式迁移引入 Workspace 和成员关系。

## 8. 推荐执行顺序

```text
P6.0 个人用户设计与交接
       ↓
P6.1 后端身份与 Session
       ↓
P6.2/P6.3 全链路数据隔离
       ↓
前端认证壳 + F2 文档管理
       ↓
F3/F4 检索与问答接入 + 双用户验收
       ↓
F5 部署与个人多用户软件闭环
       ↓
出现团队共享需求后启动 P7
```

该顺序先建立可信身份和数据边界，再开放完整文档界面，避免前端先依赖全局接口后再次返工，同时不把团队
SaaS 复杂度提前压到个人用户阶段。
