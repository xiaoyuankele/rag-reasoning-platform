# 高性能与高并发工程目标

> 状态：2026-08-21 已完成当前机器第一轮并发拐点测试，仍处于单实例、模块化单体的性能工程阶段。
> 本文描述训练目标和演进边界，不把候选压测指标当作生产 SLA。

## 1. 双重产品定位

项目同时承担两个目标：

### 1.1 可使用的个人 RAG 产品

用户可以完成：

```text
注册/登录
→ 上传自己的文档
→ 异步解析和查看 chunks
→ 关键词检索
→ 按需向量化
→ 语义检索和带来源问答
```

当前仍保持个人版、单工作区和模块化单体边界；团队工作区、成员关系和租户权限留到 P7。

### 1.2 高性能、高并发工程训练平台

同时把系统作为一个真实的性能工程练习场，重点训练：

- 异步任务和固定大小 Worker Pool；
- Python 进程复用、超时、崩溃替换和资源回收；
- PostgreSQL 事务、`SKIP LOCKED`、幂等和状态机；
- 上传、解析、向量化之间的背压和资源配额；
- 多用户公平性、限流和失败隔离；
- 阶段耗时、吞吐、P50/P95、CPU、内存和连接池观测；
- 从单实例模块化单体升级到多实例和分布式组件的路径。

“高并发”在本文中首先表示可测量、可解释、可降级的并发能力，不表示当前已经达到互联网生产级容量。

## 2. 当前架构基线

```text
Vue SPA
  → Gin API + Session/OwnerScope
  → Go Application/Domain
  → PostgreSQL + 本地文件存储
  → document_jobs / embedding_jobs
  → Go Worker Pool
  → Python oneshot 或 Python Process Pool
```

当前已经具备：

- `DOCUMENT_WORKER_CONCURRENCY`：同一实例内 1～4 个文档 Worker；
- `PYTHON_PROCESS_MODE`：`oneshot` 或 `pool`；
- Python Process Pool：固定槽位、JSON Lines、惰性启动、超时取消、崩溃替换和按任务数回收；
- PostgreSQL `FOR UPDATE SKIP LOCKED` 领取任务；
- 文档处理指标：排队、处理器、总耗时、文件大小、chunk 数和错误分类；
- 上传前 SHA-256 预检，减少同用户重复文件的传输成本；
- OwnerScope 和数据库唯一约束保证个人数据隔离与重复上传并发正确性。

代码默认仍采用保守配置；本地开发可以显式使用双 Worker 和双 Python Process Pool 做对照压测。

### 2.1 当前机器的第一轮容量事实

2026-08-21 使用固定 8 篇 PDF（共 51.28 MiB）完成第一轮并发对照。测试机器为 4 个物理核心、8 个逻辑处理器；后端容器内存上限为 768 MiB。表中的 `2/2` 表示“2 个 Go 文档 Worker / 2 个 Python Process Pool 槽位”，不是 CPU 核心数。

| 后端 CPU 配额 | Worker/Pool | 批次墙钟时间 | 相对同配额 2/2 | 后端峰值内存 |
| ---: | ---: | ---: | ---: | ---: |
| 1.5 | 2/2 | 56.762 秒 | 基线 | 约 282 MiB |
| 1.5 | 3/3 | 59.038 秒 | 慢 4.0% | 约 255 MiB（采样值） |
| 1.5 | 4/4 | 66.485 秒 | 慢 17.1% | 约 319 MiB |
| 2.0 | 2/2 | 46.076 秒 | 基线 | 约 232 MiB |
| 2.0 | 3/3 | 50.267 秒 | 慢 9.1% | 约 323 MiB |

当前机器和样本下，增加到 3/3 或 4/4 会增加 CPU 竞争和单任务尾延迟，并没有提高批次吞吐。因此本地开发推荐 `BACKEND_CPUS=2.0`、`DOCUMENT_WORKER_CONCURRENCY=2`、`PYTHON_PROCESS_POOL_SIZE=2`；稳定降级仍可使用单 Worker 和 `oneshot`。这个结论只适用于当前机器与固定样本，不是生产容量承诺。

## 3. 性能工程的衡量方式

代码行数、Worker 数量或单次秒表时间都不能单独证明高性能。每次优化需要同时记录：

| 维度 | 必须观察的指标 |
| --- | --- |
| 吞吐 | 每分钟成功文档数、每秒请求数、批次墙钟时间 |
| 延迟 | API P50/P95、任务排队 P50/P95、处理器 P50/P95 |
| 资源 | CPU、内存、磁盘 I/O、临时文件、PostgreSQL 连接池等待 |
| 正确性 | 重复领取数、重复任务数、跨用户泄漏数、失败收尾完整性 |
| 稳定性 | 超时率、进程重启数、任务恢复数、长时间运行内存增长 |
| 用户体验 | 上传等待、解析完成显示延迟、失败提示和重试成功率 |

固定真实文献集必须保留文件大小、页数、chunk 数和内容哈希，不能用每次不同的文件集合直接比较优化前后。

## 4. 分阶段工程路线

### 阶段 A：单实例并发基线（第一轮拐点已完成）

- 保持模块化单体和 PostgreSQL 任务队列；
- 使用 Go Worker Pool 并发 1、2、3 做对照；
- 比较 Python oneshot 与 Process Pool；
- 记录 CPU、内存、数据库连接池和 API 延迟；
- 固定大文档、普通文档、重复文件和失败 PDF 四类批次。

完成标准：知道当前机器在不同并发下的吞吐、排队和资源拐点，而不是只知道某一批总耗时。

第一轮已经定位当前机器的推荐点为 2.0 CPU 配额下的 2/2。阶段 A 尚需补充长时间浸泡、失败 PDF 混合批次和 API 延迟对照，避免把一次短批次结果误认为长期稳定容量。

### 阶段 B：并发正确性与背压

- 单用户活动任务数量和批量大小限制；
- 全局 Worker 上限和队列长度限制；
- 上传、解析、向量化分别限流；
- 任务幂等、取消、超时和失败隔离；
- 资源不足时使用稳定的 `429` 或 `503`，并提供 `Retry-After`；
- 失败任务不能因为统一退避阻塞健康任务。

2026-08-22 已完成阶段 B 的第一项后端切片：向量任务在入队事务内执行单用户与全局活动数量限制，
并通过 PostgreSQL advisory lock 保护不同文档并发争抢最后一个名额；单任务接口分别使用 `429/503`，
批量接口保留逐项结果。解析任务入队、上传并发及不同用户公平调度仍待后续切片，不能把本次完成扩大解释为
整个阶段 B 已完成。

同日完成第二项切片：后台向量 Worker 与在线语义能力分别使用独立容量份额，并共同受进程内远程 Embedding
全局硬上限保护。默认 Worker/Online/Global 为 2/2/4，因此后台堆积不能把在线请求完全饿死。后台任务允许等待，
在线请求限时等待并以稳定 `503` 和 `Retry-After` 拒绝；结构化事件分别记录分类和全局在途数量、等待耗时、
执行耗时与容量超时。该能力只控制单实例同时调用数，不替代提供方 RPM/TPM 限流，也尚未提供在线类别内部的
跨用户公平队列或多实例全局配额。

完成标准：高峰时系统可以拒绝或延迟新工作，但不重复执行、不跨用户泄漏、不拖垮 API。

### 阶段 C：多实例任务执行

- 任务领取增加 `worker_id`、`lease_expires_at` 和可选 heartbeat；
- 只恢复租约过期的 `processing` 任务；
- API 实例与 Worker 角色可以分开部署；
- 原始文件迁移到共享对象存储或受控共享卷；
- 任务最终状态仍由 PostgreSQL 保存。

完成标准：一个实例退出不会误重置另一个实例仍在处理的任务，也不会因为恢复逻辑造成重复写回。

### 阶段 D：按指标引入分布式组件

只有出现明确瓶颈后才引入：

- Redis：多实例共享限流、Session Cache-Aside、任务进度通知；
- 消息队列：PostgreSQL 任务队列成为实测瓶颈后再评估；
- 独立 Python 服务：需要独立扩缩容或故障隔离时再拆分；
- 读副本、分片或专用检索引擎：出现真实查询规模和数据库瓶颈后再考虑。

Redis 或消息队列都不能替代 PostgreSQL 中的正式任务状态、权限和业务事实。

## 5. 前后端开发约束

### 后端

- 业务层只依赖 `DocumentProcessor` 等稳定端口，不依赖具体 Python 生命周期；
- Worker 并发必须有配置上限，不能按请求无限启动 goroutine 或 Python 进程；
- `queued`、`processing`、`succeeded`、`failed` 的语义必须由服务端决定；
- 每次并发优化必须补充任务领取、失败收尾、取消和 shutdown 测试；
- API、Worker、Python 进程和数据库连接池要分别计量。

### 前端

- 浏览器上传并发不等于后端解析并发；
- 预检哈希只是性能优化，后端上传哈希和数据库唯一约束仍是最终裁判；
- `queued` 显示为排队中，终态必须重新读取文档确认；
- 批量导入保留单项失败隔离，不通过无限提高浏览器并发弥补后端排队；
- 遇到 `429/503` 按契约退避，不把临时容量不足显示成永久业务失败。

## 6. 当前非目标

- 当前不承诺公网生产级 QPS 或严格 SLA；
- 当前不直接实现微服务、多活和多地域部署；
- 当前不为展示架构而提前引入 Redis、Kafka 或 Kubernetes；
- 当前不把高并发训练目标扩张成更多无关业务功能；
- 当前不以代码行数作为性能或工程质量的唯一评价标准。
