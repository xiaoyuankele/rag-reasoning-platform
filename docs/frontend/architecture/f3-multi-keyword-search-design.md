# F3 多关键词与位置范围检索设计

> 状态：方案待前后端确认，尚未实现。当前 `GET /search?q=...` 仍把 `q` 当作一个连续字面查询串。

## 1. 需要区分的检索语义

| 模式 | 示例 | 准确含义 |
| --- | --- | --- |
| 完整短语 | `磁浮 振动` | 连续出现完整字符串，保持当前行为 |
| 全部关键词 | `磁浮`、`振动` | 每个词都必须出现，顺序和距离不限 |
| 任一关键词 | `磁浮`、`振动` | 至少出现一个词 |

“出现在哪里”还需要单独定义：

- `chunk`：全部词出现在同一文本块；当前数据库已经具备该数据单位；
- `sentence`：全部词出现在同一句；需要后端可靠识别并保存或查询句子边界；
- `paragraph`：全部词出现在同一自然段；当前 chunk 不等于自然段，PDF 提取也未必保留可靠段落边界，不能直接冒充。

## 2. 推荐兼容契约

保留现有 `q` 作为完整短语，新增重复查询参数表达明确的多词输入：

```http
GET /search?term=磁浮&term=振动&operator=all&within=chunk&page=1&page_size=10
```

- `term`：重复参数，建议 2～8 个，去空白、去重并限制单项与总字符数；
- `operator`：`all | any`；
- `within`：第一阶段只实现 `chunk`，第二阶段增加 `sentence`；
- `q` 与 `term` 不同时提供，避免语义冲突；
- `document_id`、OwnerScope、ready 状态、分页和错误边界继续复用现有规则；
- 响应应回传规范化 `terms`、`operator` 和 `within`，供 URL 恢复、标题和高亮使用。

前端不能针对每个词分别调用一次 `/search` 后自行取交集或并集。这会破坏统一分页、总数、排序、去重和错误语义。

## 3. 前端交互

```text
关键词标签输入（Enter 添加）
├─ 匹配方式：完整短语 / 包含全部 / 包含任一
└─ 位置范围：同一文本块 / 同一句
```

- 每个关键词以可删除标签展示，避免用户猜测空格怎样解析；
- URL 保存词项与模式，刷新和返回后可以恢复；
- 结果卡高亮全部词项，可使用有限色板，同时保留粗体等非颜色提示；
- 空结果说明当前是 AND/OR、chunk/sentence 中的哪一种组合；
- `sentence` 未由后端支持前，界面不显示可点击的假选项。

## 4. 后端实现顺序

### 第一阶段：同一文本块

在现有 OwnerScope + ready 文档 SQL 上组合字面条件：`all` 使用 AND，`any` 使用 OR。count 与 data SQL 必须使用完全
一致的词项、文档和用户过滤条件。该阶段不需要修改文档解析结构，可以先形成可用闭环。

### 第二阶段：同一句

不能先按 chunk 分页再由 Go 过滤句子，否则结果页数量、总数和翻页都会不准确。推荐解析时保存句子单位，例如：

```text
text_sentences(id, chunk_id, sentence_index, content)
```

搜索先在句子单位判断全部词是否共现，再返回父文本块和命中的句子摘录。中文至少识别 `。！？`，英文识别 `.?!`，并为
缩写、小数和 PDF 异常换行建立测试。若未来需要“同一自然段”，处理器还必须显式保存 block/paragraph 边界。

## 5. 推荐迭代

1. 先交付 2～8 个关键词的 `all/any + within=chunk`；
2. 前端标签输入、URL 恢复、模式说明和多词高亮同步接入；
3. 后端补句子索引与正确分页后，再开放 `within=sentence`；
4. “同一自然段”和 PDF 原页跳转独立评估，不与第一批多词检索混在一起。

当前 chunk 仍以字符上限切分为主，不等同于自然段或句子。实施本方案前应同时阅读
[F3 检索对 Chunk 质量的依赖](f3-chunk-quality-dependency.md)，并在界面中使用准确的“同一文本块”表述。
