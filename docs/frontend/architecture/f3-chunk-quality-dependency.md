# F3 检索对 Chunk 质量的依赖

> 状态：跨端质量依赖，尚未实施新的分块算法。前端可以展示和筛选结果，但不能修复处理阶段已经丢失的段落、句子与版面结构。

## 1. 当前实现事实

- Markdown/TXT 由 Go 文本分块器处理，默认上限为 1000 个 Unicode 字符；
- 文本处理会把换行、制表符和连续空白折叠成一个空格，优先在上限前的空格处切分；
- 中文长文本在没有空格时会按字符上限硬切；
- PDF 由 pypdf 逐页提取，每页规范化为空格文本，再用同类 1000 字符上限切分；
- PDF chunk 不跨物理页，能够保留页码，但当前没有 overlap、标题路径、自然段、句子、字符偏移或版面 block 元数据；
- 双栏阅读顺序、页眉页脚、断词、表格、公式和图注仍属于 PDF-4 质量改进范围。

因此，当前 `chunk` 是稳定的存储与检索单位，不是严格的自然段或语义段。

## 2. 对检索功能的影响

- 两个词分落相邻 chunks 时，`within=chunk + operator=all` 会漏检；
- 一个 chunk 可能包含多个自然段，因此“同一 chunk”不能宣称“同一段”；
- 换行已经折叠后，前端无法恢复原始段落和句子边界；
- 不完整句子、重复页眉页脚和双栏错序会降低向量表示、Top K 证据与最终回答质量；
- overlap 可以改善边界召回，但会引入重复命中、重复向量和回答证据去重问题。

## 3. 推荐优化顺序

1. 先建立可复现质量样本：中英文、单/双栏、页眉页脚、表格、公式、Markdown 标题和长中文段落；
2. 提取阶段尽量保留页、block、段落、标题路径和句子边界，不要先全局折叠后再猜结构；
3. 分块器优先按标题 → 段落 → 句子切分，最后才按字符/Token 上限硬切；
4. 用真实模型 Token 预算配置目标大小，并通过样本评估 overlap，而不是固定一个未经测量的经验值；
5. 为 chunk 保存 `chunking_version`、section/paragraph/sentence 定位和可选字符范围；
6. 用关键词召回、语义 Recall@K、边界完整率、重复率和来源定位准确率做前后对照。

## 4. 版本与重建边界

分块算法变化会改变 chunk ID、内容和向量，不能只修改新文档：

```text
新 chunking_version
→ 文档重新解析
→ 原子替换旧 chunks
→ 旧 embeddings 失效
→ 按当前模型重新向量化
→ 文档重新进入 AI-ready
```

前端应展示重新解析/重新向量化状态，但不在浏览器内执行分块。后端需要保证替换、任务幂等、失败恢复和 OwnerScope；
历史新旧版本不能在没有标识的情况下混合比较。

## 5. 与多关键词检索的关系

`all/any + within=chunk` 可以先实现为最小能力，但产品文案必须称为“同一文本块”。精确“同一句”应在句子边界可用后实现；
精确“同一自然段”还依赖处理器保存 paragraph/block。分块质量与版本策略冻结前，不应把当前 chunk 提升成更强的语义承诺。
