# 100 人在线并发演进：前端开发交接

> 状态：2026-08-29 F100-1 与 F100-2 前端切片已实现；Embedding/Answer 及文档上传/解析容量状态、
> `Retry-After` 冷却和手动重试已接入，真实容量联调待执行。
>
> 前端不负责调度 Python、抢占数据库任务或推断系统容量；前端负责有限并发、正确展示异步状态、遵守 Retry-After，并让用户理解“已接收、排队、处理中、完成、暂时拒绝”的差异。

## 1. 当前前端基础

当前 Vue 前端已经实现：

- Session 恢复、受保护路由和统一 401 处理；
- Web Worker 分块 SHA-256、上传预检、有限上传并发；
- 文档解析与向量任务状态轮询；
- 向量化页面的单篇/批量申请、最近任务恢复与 waiting/queued/processing 轮询；
- 关键词检索页面和带来源问答页面的加载、超时、失败、功能关闭和来源展示；
- ApiError 中的 HTTP 状态、稳定 code、X-Request-ID 与 Retry-After。

当前客户端保守基线为：哈希并发 1、上传并发 2、任务轮询使用非重叠的递归定时器。该设置不应因后端 Worker 数量变化而自动放大。

## 2. 前端不变原则

1. 业务 DTO 不携带 user_id、Worker 数、Python Pool 大小、队列内部序号或数据库连接池信息。
2. 上传成功、POST 返回 202、任务开始处理、任务完成是不同状态；页面必须依据服务端任务状态渲染。
3. 用户点击重试不等于立即重放网络请求。收到 429/503 时优先读取 Retry-After。
4. 文档解析、向量化和问答是三类独立资源，不能用同一个无限重试器处理。
5. 前端本地缓存只能保存展示和草稿；不能缓存 Session、私有 PDF 正文或跨用户任务结果。
6. 页面隐藏、切换用户、退出登录或组件卸载时，应停止无意义轮询和未完成请求。

## 3. F100-1：统一容量错误与退避

目标是把所有容量错误从“普通失败”变成可恢复状态。

当前 shared 契约已经冻结第一批容量结果，前端应统一处理：

| 后端结果                                    | 页面语义                            | 前端动作                                                |
| ------------------------------------------- | ----------------------------------- | ------------------------------------------------------- |
| `429 embedding_owner_active_job_limit`      | 当前用户活动向量任务达到上限        | 保留选择，按 `Retry-After` 等待并刷新已有任务           |
| `503 embedding_queue_capacity_exhausted`    | 全局活动向量任务达到上限            | 保留操作上下文，按 `Retry-After` 提供手动或一次受控重试 |
| `503 embedding_provider_capacity_exhausted` | 在线 Embedding 本地并发槽位等待超时 | 保留查询或选择，不把它误写成远程供应商故障              |
| `503 answer_capacity_exhausted`             | Answer 本地并发槽位等待超时         | 保留问题与范围，按 `Retry-After` 提供稍后重试           |
| `429 upload_owner_concurrency_exhausted`    | 当前用户上传并发槽位暂满            | 保留文件，按 `Retry-After` 后手动重试                   |
| `503 upload_capacity_exhausted`             | 全局上传槽位暂满                    | 保留文件与请求编号，不立即重复上传                      |
| `429 processing_owner_active_job_limit`     | 当前用户活动解析任务达到上限        | 保留文档，等待或取消已有 queued 任务                    |
| `503 processing_queue_capacity_exhausted`   | 全局解析队列暂满                    | 保留文档，按 `Retry-After` 后手动重试                   |
| 409 + document embeddings not ready         | 前置向量尚未完成                    | 引导至向量化页，不把它显示成模型故障                    |
| 401 authentication_required                 | Session 失效                        | 清理受保护页面临时状态，进入登录流程                    |

实现要求：

- 在 shared/api 错误转换层统一解析 Retry-After 为安全秒数；
- feature composable 接收“是否可重试、何时可重试”的结构化状态，而不是比较英文 message；
- 重试使用 setTimeout 且必须可取消；禁止 setInterval 叠加请求；
- 同一项容量拒绝在等待期内只允许一个计时器；
- 前端不伪造“队列第几位”或“还剩多少秒”，除非后端未来提供经过定义的字段。

2026-08-23 已完成的前端切片：

- `shared/api` 使用稳定 code 生成容量展示事实，并把 `Retry-After` 转为单一、可取消的冷却倒计时；
- 向量化单篇 429/503 保留原选择；批量 200 能识别逐项 `rate_limited/capacity_exhausted`，保留已成功任务并暂停后续拆批；
- 问答容量拒绝保留问题、文档范围与请求编号，等待期间不允许第二个 POST；
- 倒计时到期只开放手动重试，不自动重放可能产生费用的问答或批量向量命令；
- 页面显示的是“距离允许再次尝试的冷却时间”，不是队列位置、系统恢复预测或任务预计完成时间。

## 4. F100-2：上传与解析队列体验

文档导入页面继续保持：

    哈希 -> 预检 -> 上传 -> 创建解析任务 -> 观察终态

新增状态建议：

| 状态               | 用户看到的文案方向       | 是否允许重试              |
| ------------------ | ------------------------ | ------------------------- |
| local_waiting      | 等待本地处理             | 可以取消                  |
| hashing            | 正在计算文件摘要         | 可以取消后续上传          |
| uploading          | 正在上传                 | 依据请求状态              |
| accepted           | 已接收，等待创建解析任务 | 不把它写成“解析完成”      |
| queued             | 已进入解析队列           | 继续观察                  |
| processing         | 正在解析                 | 继续观察                  |
| rate_limited       | 当前账户任务数量达到上限 | 到期后手动/受控重试       |
| capacity_full      | 系统任务容量暂满         | 到期后手动/受控重试       |
| succeeded / failed | 最终状态                 | failed 按正式错误契约重试 |

即使用户一次选择很多文件，浏览器仍以有限上传并发发送。收到单项 429/503 时只暂停受影响项，不取消已经在上传或已入队的其他文件。

2026-08-29 已实现：容量拒绝继续使用原阶段失败状态保存文件和请求编号，并在批次顶部显示结构化原因；单一冷却期间
禁止“重试失败项”，倒计时结束后只开放手动重试。解析详情页和批量项都可以取消后端确认 `cancelable:true` 的 queued 任务；
刷新或 409 后通过 `POST /processing-jobs/latest` 恢复真实任务，不再把停止本地请求冒充服务端取消。

## 5. F100-3：任务轮询与未来通知

当前轮询继续是正式降级路径：

- 文档解析任务只轮询活动 job，终态后重新读取文档；
- 向量化页面仅轮询 waiting_document、queued、processing；
- 问答请求是一次性请求，不转化为后台无限轮询；
- 页面不可见时暂停或降低轮询，恢复可见后先同步一次；
- 网络离线、退出登录和文档删除后取消对应请求。

P100-4 如加入 SSE、WebSocket 或 Redis Pub/Sub，前端采用“通知触发一次 GET 刷新”的方式，不把通知载荷当成正式状态。通知缺失、连接中断或浏览器后台节流时必须退回现有 GET 轮询。

## 6. F100-4：100 用户下的前端资源边界

前端的目标是减少无意义压力，而不是在浏览器侧实现全局调度：

| 场景         | 当前或目标策略                                             |
| ------------ | ---------------------------------------------------------- |
| 文件哈希     | Dedicated Worker，单路、分块读取                           |
| 上传         | 固定有限并发；默认不因后端扩容而提高                       |
| 预检         | 网络/5xx 失效开放，确定性 400/401/413 不绕过               |
| 文档轮询     | 单 job 非重叠；终态后停止                                  |
| 向量任务发现 | 文档 ID 最多 100 项一批；只轮询活动任务                    |
| 搜索         | 输入提交触发，不在每个键入事件调用后端                     |
| 问答         | 仅用户显式提交；新问题取消旧请求；容量失败遵守 Retry-After |

不在 Pinia 中保存批量上传的全部瞬态细节、搜索结果或问答正文；跨页面只保留认证和真正需要共享的状态，避免 100 用户场景下前端自己造成内存与状态错配。

## 7. 前端测试与联调清单

### 自动化测试

2026-08-23 已覆盖第一批容量交互：四个稳定 code、批量 200 响应头、单一计时器、等待期重复提交保护、部分成功保留和问答不自动重放。

- 429 owner limit、503 global capacity、503 provider capacity 均能展示稳定文案和 Retry-After；
- 同一项重试不会产生两个并发计时器或重复 POST；
- 切换页面、隐藏页面、退出登录、删除文档时轮询会停止；
- 批量导入中一项限流不会覆盖其他项状态；
- 202 只显示“已接收/排队”，不会显示为 ready；
- 409 embeddings not ready 能正确引导用户，不发起无证据问答；
- X-Request-ID 在错误界面保留给排障。

### 联调验收

| 场景                    | 前端预期                                                        |
| ----------------------- | --------------------------------------------------------------- |
| 后端拒绝第 N 个解析任务 | 当前项保留在 rate_limited/capacity_full，可恢复；其他项不受影响 |
| Worker 忙但 API 正常    | 上传/创建任务接口快速给出 accepted 或容量响应，页面不假死       |
| 任务跨设备完成          | 刷新后从服务端读取真实文档和任务状态                            |
| Redis/通知不可用        | UI 继续通过轮询得到终态                                         |
| Session 失效            | 不继续轮询私有资源，不泄露上一用户的局部结果                    |

## 8. 与后端的冻结点

当前已经冻结：

1. 向量任务 owner/global 容量错误的 HTTP、稳定 code 和 `Retry-After`；
2. 同一文档活动任务的幂等复用优先于容量拒绝；
3. 批量向量化的 `capacity_exhausted` 逐项结果；
4. 在线 Embedding 与 Answer 本地容量闸门的 `503` code 和 `Retry-After`。

后续仍需冻结或验证：

1. 当前单文件上传接口在批量编排中的真实容量联调结果；第一版不新增批量上传 DTO；
2. 多实例后任务状态字段是否保持不变；worker_id、租约等内部字段不得进入前端 DTO；
3. 进度通知的事件名、最小载荷、断线策略和轮询回退规则。

前端不得依赖尚未实现的 queue_position、estimated_wait_seconds、SSE 或 WebSocket 字段。
