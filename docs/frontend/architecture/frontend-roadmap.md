# 前端分层与阶段路线

## 1. 核心目的

为文档上传、处理状态、检索和带来源问答提供一个轻量、可理解、可测试的用户界面，
同时避免页面组件直接耦合后端 JSON 和 HTTP 细节。

## 2. 已确认分层

```text
页面/路由
  ↓ 组合功能
功能模块（文档、检索、问答）
  ↓ 调用
应用状态与用例
  ↓ 使用
API Client + DTO 转换
  ↓ HTTP
Go 后端
```

- 页面与组件：负责展示和用户交互；
- 功能模块：围绕“上传文档”“搜索”“提问”等用户动作组织；
- 状态与用例：管理加载、成功、空结果和失败状态；
- API Client：唯一负责 URL、请求方法、请求体和响应解析；
- DTO/类型转换：隔离后端契约与前端视图模型；
- 测试：优先验证用户行为和错误状态，不复制后端内部实现。

具体目录、依赖方向、状态归属、技术栈和测试策略见
[前端应用架构](frontend-application-architecture.md)。

## 3. 分阶段路线

- `F0` 技术栈与工程骨架：确定框架、构建工具、格式化、测试与目录；
- `F1` API 基础：建立统一 Client、环境配置、错误模型和健康检查；
- `F2` 文档管理：上传、列表、详情、删除、解析任务状态；
- `F3` 检索：关键词检索、筛选、分页、来源与页码展示；
- `F4` AI 能力：语义检索、带来源问答、加载/超时/费用提示；
- `F5` 工程化：端到端测试、可访问性、性能、构建和部署。

## 4. 原 F0～F1 非目标

- 不先实现复杂设计系统；
- 不把所有后端接口一次性接完；
- 不在页面组件里散落 `fetch` 调用；
- 不在前端复制 Go 的领域规则；
- 不默认启用会产生远程模型费用的能力；
- F0～F1 不实现登录、注册、成员管理和租户切换；这描述的是已完成阶段的历史边界。

## 7. P6 个人用户前端切片（第一批与真实认证纵向联调已完成）

- 后端 `P5` 负责运行路径、配置、日志、部署、备份和可观测性，不等于前端开发；
- P6 后端 B1～B7、验证码、注册、登录、当前用户、退出、忘记/重置密码和全链路 OwnerScope 隔离均已完成；
- P6 前端增加 `entities/user`、`features/auth`、登录/注册/忘记密码页面和全局 Auth Store；
- 应用启动时 `/users/me` 决定 `unknown → authenticated/anonymous`，避免认证状态未确定时闪现受保护页面；
- 业务 API 不传 `user_id`，同源浏览器自动携带 `HttpOnly` Cookie；
- 统一 API Client 遇到稳定 `401 authentication_required` 时清理 Auth Store 并跳转登录，登录接口本身
  不进入重定向循环；
- Router Guard 只负责界面导航，真正隔离仍必须在后端 Application 与 Repository 生效；
- 登录后继续复用 F2～F4 的文档、检索和问答模块，不为每个用户复制一套页面；
- 工作区选择、成员管理和角色权限属于 P7，不进入 P6 UI。
