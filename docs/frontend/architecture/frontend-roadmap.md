# 前端分层与阶段路线

## 1. 核心目的

为文档上传、处理状态、检索和带来源问答提供一个轻量、可理解、可测试的用户界面，
同时避免页面组件直接耦合后端 JSON 和 HTTP 细节。前端也参与高性能工程目标：通过上传并发、哈希预检、
任务轮询、退避和用户可感知状态，配合后端验证端到端吞吐与体验，而不是自行复制后端并发规则。

## 2. 已确认分层

```text
页面/路由
  ↓ 组合功能
功能模块（文档、检索、问答）
  ↓ 调用
应用状态与用例
  ↓ 使用
API Client + DTO 转换
  ↓ HTTP
Go 后端
```

- 页面与组件：负责展示和用户交互；
- 功能模块：围绕“上传文档”“搜索”“提问”等用户动作组织；
- 状态与用例：管理加载、成功、空结果和失败状态；
- API Client：唯一负责 URL、请求方法、请求体和响应解析；
- DTO/类型转换：隔离后端契约与前端视图模型；
- 测试：优先验证用户行为和错误状态，不复制后端内部实现。

具体目录、依赖方向、状态归属、技术栈和测试策略见
[前端应用架构](frontend-application-architecture.md)。
性能目标、压测口径和跨端约束见
[高性能与高并发工程目标](../../shared/architecture/performance-engineering-goal.md)。

## 3. 分阶段路线

- `F0` 技术栈与工程骨架：确定框架、构建工具、格式化、测试与目录；
- `F1` API 基础：建立统一 Client、环境配置、错误模型和健康检查；
- `F2` 文档管理：上传、列表、详情、删除、解析任务状态；
- `F3` 检索：关键词检索、筛选、分页、来源与页码展示；
- `F4` AI 能力：语义检索、带来源问答、加载/超时/费用提示；
- `F5` 工程化：端到端测试、可访问性、性能、构建和部署。

## 4. 原 F0～F1 非目标

- 不先实现复杂设计系统；
- 不把所有后端接口一次性接完；
- 不在页面组件里散落 `fetch` 调用；
- 不在前端复制 Go 的领域规则；
- 不默认启用会产生远程模型费用的能力；
- F0～F1 不实现登录、注册、成员管理和租户切换；这描述的是已完成阶段的历史边界。

### 7.5 高性能与高并发目标的前端对齐

项目仍是个人版模块化单体，前端不会因为后端增加 Go Worker Pool 和 Python Process Pool 就引入微前端、Redis 客户端或
浏览器侧任务调度器。前端承担的是端到端入口和反馈：

- 保持哈希并发 1、上传并发 2 和集中有限轮询，后端并发配置不直接映射到浏览器；
