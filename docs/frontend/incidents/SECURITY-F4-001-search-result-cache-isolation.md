## 2. 事件摘要

前端调试过程中，为解决“刷新后检索结果消失”，曾把关键词和语义检索的完整结果 JSON 写入两个固定的 `localStorage` key：

```text
rag-workspace:keyword-search:last-result
rag-workspace:semantic-search:last-result
```

结果包含文档名称、页码和文本块正文。两个 key 没有绑定当前用户，也没有保存期限、退出清理和完整运行时校验。同一浏览器如果从账户
A 切换到账户 B，页面可能恢复出 A 的旧结果；恶意或损坏的浏览器存储也可能进入视图模型。

该实现只存在于本地调试提交 `8dbf67e`，在推送前审查中被发现。该本地提交随后被改写，没有进入远程历史。

## 3. 时间线与提交证据

1. `68de968`：正式语义检索基础页面提交并推送，尚不保存检索结果；
2. 本地调试阶段：增加语义文字高亮和全局 `localStorage` 最近结果缓存；
3. `8dbf67e`：调试对话创建本地提交，但未推送；
4. 前端开发对话执行提交前范围与安全审查，发现无用户隔离、永久保存正文和校验不足；
5. `46d494e`：不安全本地提交被改写为用户/范围隔离的 `sessionStorage` 方案并推送；远程没有出现 `8dbf67e`；
6. `0d84131`：完成生产安全加固并推送，包括默认关闭、显式选择、30 分钟 TTL、认证匿名化清理和旧缓存迁移；
7. 本文档提交：形成可从正式前端文档、问题档案和 Git 历史互相倒查的记录。

## 4. 影响与事实边界

已经确认：

- 不安全实现曾在本地工作树和本地提交中存在；
- 如果当时在调试页面完成过检索，浏览器可能写入上述两个旧 key；
- 保存内容可能包含当前账户私有文档的文本块正文；
- 不安全提交没有推送 GitHub，远程分支未发布该版本；
- 当前代码进入检索页会删除两个旧 `localStorage` key 和旧的自动 `sessionStorage v1` key。

没有证据证明：

- 缓存内容被上传到后端之外的第三方；
- 另一账户实际读取过这些内容；
- 发生了外部数据泄露或已经构成监管认定的违法事件。

若以后发现新的访问日志、浏览器镜像或用户报告，应重新打开本事件，不得用当前“未发现”结论覆盖新证据。

## 5. 根因分析

### 5.1 直接原因

把“刷新恢复”直接实现为固定 key 的完整结果永久缓存，没有把文档正文识别为当前用户的私有数据。

### 5.2 流程根因

- 前端调试对话承担了业务代码修改，却没有先执行前端开发协议中的架构、数据边界和完成标准说明；
- 设计前没有回答“保存什么、为谁保存、保存多久、何时删除、缓存损坏怎么办”；
- 原提交没有增加缓存恢复、跨用户隔离、退出清理和损坏数据的专门测试；
- 提交动作只完成本地 commit，没有执行默认的远程推送和最终工作区报告；
- 检索 feature 当时没有获得可信的当前用户公开 ID，导致使用了全局 key。

### 5.3 为什么提交前才发现

页面功能测试只验证“刷新后还能看到结果”，这个正向场景无法暴露账户切换、长期保存和存储污染问题。缺陷由主前端对话在推送前
检查提交差异、认证边界和浏览器存储方式时发现。

## 6. 永久修复

当前实现遵守以下规则：

- 关键词检索不缓存正文，刷新时使用 URL 参数重新执行无远程模型费用的 GET；
- 语义结果保留默认关闭，页面明确说明会保存返回的文本片段；
- 只有用户显式开启后才保存；在成功结果已经显示时开启，也会立即按同一规则保存；
- 使用当前标签页 `sessionStorage`，key 和内容都绑定公开用户 ID；
- 恢复时必须同时匹配全部/单篇文档范围，并完整校验 query、top_k、ID、页码、正文和 similarity；
- 缓存最长 30 分钟，过期读取时立即删除；
- 关闭选项、退出登录、`401 authentication_required`、密码重置和用户切换会清理私有会话缓存；
- 登录恢复只保留当前用户命名空间，清除当前标签页中其他用户的项目私有缓存；
- 旧的全局 `localStorage` 和自动 `sessionStorage v1` key 会被迁移清理；
- 缓存永远不能代替后端 Session、OwnerScope、文档存在性或 AI-ready 判断。

主要修复文件：

- `web/src/features/search/model/semantic-search-cache.ts`；
- `web/src/shared/storage/private-session-storage.ts`；
- `web/src/features/auth/store/auth-store.ts`；
- `web/src/features/search/ui/SemanticSearchPanel.vue`。

## 8. 强制预防清单

以后新增或修改 `localStorage`、`sessionStorage`、IndexedDB、Service Worker Cache 或前端下载缓存时，必须在编码前回答并记录：

1. 保存的数据是否包含正文、身份、联系方式、Token、摘要或可关联用户的标识？
2. 为什么不能只保存在内存、URL，或由受 Session 保护的后端重新读取？
3. 是否默认关闭，用户是否知道保存内容和用途？
4. key 是否绑定当前用户和业务范围？
5. 保存期限是多少，过期、退出、401、密码重置、切换用户和删除文档时如何清理？
6. 浏览器存储被修改、损坏、写满或禁用时如何安全退化？
7. 是否有跨用户、跨范围、TTL、退出清理和旧版本迁移测试？
8. 是否使用 Vue 文本插值并避免把缓存正文写入 `v-html`？
9. 前端正式文档、问题档案、每日复盘和验证数字是否同步？
10. 提交前是否检查 `rg -n "localStorage|sessionStorage|indexedDB|caches\." web/src` 的新增调用？

任一问题没有明确答案时，不得把完整用户数据写入浏览器持久化存储。
