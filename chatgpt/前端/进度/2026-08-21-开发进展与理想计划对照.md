## 五、当前边界

- 不修改后端代码，不直接调用远程 Embedding API；
- 不把向量任务逻辑放入 `features/documents`；
- 不把 Session Storage 当权限或永久历史；
- 不把文档 `ready` 当作向量 `succeeded`；
- 不允许 100 个任务各自建立独立定时器；
- 不在没有后端事实时显示“从未向量化”。

## 六、下一步优先级

1. 用已解析真实文档完成创建、轮询成功和 Token 显示；
2. 用解析中或失败文档验证 waiting_document 与取消；
3. 验证 Worker 领取后的 409 重新同步；
4. 后端补齐按 document 查询最新任务或任务列表；
5. 接入费用/配额/背压提示；
6. 再评估批量上传结束后的快捷入口和语义检索联动。

## 七、解析状态澄清与全部文档操作增量

真实数据只读核验显示，当前账号 94 篇文档为 `ready`、2 篇为 `failed`，没有 `uploaded`；所有 ready 文档均存在 chunks。
因此页面看到的“已解析”在数据上成立，但容易被误读为“已向量化”。本轮改为持续显示“文本……”和“向量状态……”，
并在筛选项中固定展示未解析分类及数量，即使当前数量为 0 也不会消失。

“全部文档向量化”使用当前文档列表中没有已知成功/活动任务的全部文档，不受当前搜索和解析筛选影响。提交前显示数量、
批次数和非 ready 数量；超过后端 100 项上限时顺序拆批。`uploaded/processing/failed` 会由后端创建
`waiting_document`，不会被前端伪造成已完成。

向量状态筛选目前明确标注“当前会话”。现有后端只能按已知 job ID 查询，因此刷新到无法恢复的历史任务或换设备后只能显示
“未跟踪”。若要形成长期准确的全库分类，后端还需提供批量按 document IDs 查询最新任务或分页列出任务的发现接口；前端
不能为每篇文档发起一次查询，也不能把 `untracked` 推断成“未向量化”。
