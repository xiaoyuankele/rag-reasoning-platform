# 2026-08-21 学习与架构复盘：向量状态、检索与带来源问答

## 一、今天解决了什么

今天先把后端向量任务能力变成独立工作区，再接入最近任务发现和同一 chunk 多关键词检索；最后用正式 `/answers` 契约
替换问答占位页，形成“显式提问 → 语义证据 → 回答与引用”的前端基础闭环。

## 二、完整数据流

```text
EmbeddingsPage
  → EmbeddingWorkspacePanel：筛选、选择和状态展示
  → useEmbeddingWorkspace：批量编排、逐项结果、集中轮询和取消
  → embedding-api：HTTP 状态与 unknown DTO 运行时校验
  → Go API：保存任务意图、查询或取消任务
  → PostgreSQL embedding_jobs：任务状态真相
  → Embedding Worker：调用模型并原子保存向量与成功状态
```

文档库只提供已有 `listDocuments` API 积木。向量模块没有修改 `DocumentLibraryPanel` 或上传队列，页面路由负责把两个
能力放在同一应用中，因此“文档管理”和“向量任务生命周期”可以分别演进和测试。

## 三、关键架构认识

### 1. TypeScript 类型不能代替 HTTP 运行时校验

Axios 泛型只能表达开发时预期，不能证明真实后端响应正确。向量 API 先以 `unknown` 接收，再核对六种状态、整数、时间、
可空 Token 字段和批量逐项结构。单篇响应还必须属于请求的 document ID，批量响应必须为每个请求 ID 返回且只返回一次。

### 2. 前端提交意图，不调度模型

浏览器只调用创建任务接口。排队顺序、并发、重试和远程模型调用属于后端 Worker；前端最多 4 路并发查询只是读取状态，
不能与后端 Worker 并发配置绑定。

### 3. 一个调度器优于每行一个定时器

如果每个文档行都建立 `setInterval`，100 个活动任务会产生 100 套独立节奏、重叠请求和复杂清理。当前 composable 使用一个
递归调度器，分组执行最多 4 路查询；没有活动任务就停止，页面隐藏就暂停，恢复可见后立即同步。

### 4. “没有信息”不能伪装成业务事实

后端已新增按一批 document IDs 查询最近任务的接口，页面不再依赖当前浏览器会话保存 job ID，也不会为每篇文档产生 N+1 请求。
不过 `job:null` 和最新任务 `succeeded` 都有边界：前者只说明查询结果没有可见任务，后者只说明最近任务成功，均不能证明
当前 document revision 已经 AI-ready。页面分别显示“无任务 / 状态未知 / 最近任务成功”，OwnerScope 仍由后端保证。

### 5. 解析 ready 与向量 succeeded 是两件事

文档 `ready` 表示 chunks 可用；只有向量任务 `succeeded` 才表示本轮模型向量已经生成。前端分别展示两套状态，不能因为
文档可关键词检索就直接声称它可语义检索。

### 6. 后端单批上限不应该成为前端“全库操作”上限

后端 `POST /embedding-jobs/batch` 最多接受 100 个 ID，这是单个请求的容量边界，不代表用户只能管理 100 篇文档。
前端可以提供“全部文档向量化”，但必须在确认后顺序拆成 100 项以内的批次。顺序提交比一次并发发出所有批次更容易控制
流量和反馈；若后续批次因网络失败停止，前序批次已经创建的任务必须继续保留，页面同时说明已处理数量。

### 7. 状态准确还不够，名称也要阻止错误理解

只读数据核验显示当前账号没有 uploaded 文档，ready 文档也全部存在 chunks，原页面并未伪造后端状态。问题来自“已解析”
与向量操作处在同一行，用户自然可能把它理解为“已完成向量化”。因此解析标签统一加“文本”前缀，向量提示统一加“向量状态”
前缀；未解析筛选即使数量为 0 也常驻，状态空间对用户保持完整。

页面结构还必须让两套状态对等存在，而不只是给向量状态留一行小字。本轮先增加独立状态筛选和计数，随后接入批量最近任务
发现，用 none、unknown、waiting_document、queued、processing、succeeded、failed、canceled 表达完整页面状态。

### 8. 批量发现只负责“冷启动快照”，活动状态才继续轮询

页面加载时按后端上限把 document IDs 分成最多 100 项的批次，只调用一次 `/embedding-jobs/latest`。每个结果都必须校验
document ID、顺序和 job 归属。发现后仅 waiting_document、queued、processing 继续用已有 job ID 集中轮询；成功、失败、
取消和无任务不会产生持续网络请求。这样既解决刷新/换设备恢复，也避免“批量接口之后仍然逐篇轮询全部文档”的新 N+1。

### 9. 多关键词的组合语义必须由后端决定，前端只表达并保存选择

旧 `q` 是连续完整短语；新 `term` 是 2～8 个离散关键词，`all/any` 决定同一 chunk 中的组合关系。前端使用标签输入、
URL query 和多词高亮表达这套契约，但不能自行把多个单词分别请求后合并，也不能把 `within=chunk` 写成“同一句”。
重叠关键词高亮采用长词优先并输出普通文本节点和 `<mark>`，不使用 `v-html`。

### 10. 带来源问答不是一个普通聊天框

问答请求会先做在线 query embedding 和证据检索，有证据后才调用 Generation，因此它同时涉及向量就绪、远程费用、超时和
来源可信度。页面必须让用户显式提交，不能在挂载、输入或范围切换时自动请求；409 必须引导完成向量化，不能退回自由回答。

第一版保持单次问答而不是伪装成多轮对话。`AnswerPage` 只组合共享文档范围和问答 feature；问题、结果和错误留在局部
composable，不写入 URL、Pinia 或浏览器持久存储。答案中的 `[1]` 只在响应来源连续编号通过运行时校验后展示。

### 11. 功能关闭也是正式可观察状态

生产路由只在 `ANSWER_ENABLED=true` 时注册；关闭时 `/answers` 返回普通 404，而所选文档不存在也可能返回 404。前端根据
后端安全消息区分：明确 `document not found` 才解释为文档问题，普通路由 404 解释为问答开关未启用。真实验收保持开关关闭，
证明页面不会为了测试擅自产生模型费用。

### 12. 工作目录当前分支也是运行时的一部分

前端提交 `388ab0b` 已经保存多关键词检索、向量状态发现和完整问答页，但共享工作目录一度停留在没有包含该提交的
`codex/backend-concurrency-hardening`。Vite 会直接读取当前工作目录，分支切换后会热更新成该分支中的旧前端，因此页面上的
多关键词选项和向量状态看起来像被删除；实际代码仍同时存在于本地分支和远程分支。

排查时还发现后端分支工作区有一份未提交的简化 `AnswerPage.vue`。它没有独有业务能力，且会与 `388ab0b` 中已经分层、测试过的
完整实现冲突，所以不能把“先提交所有脏文件”当作机械规则。正确做法是先识别文件来源和权威版本，再以完整前端分支为基础合入
纯后端提交。最终提交 `9dea1d4` 已完成前后端整合，`1871f2c` 固化换行规则；本地与远程统一分支一致且工作区干净。

这次事件说明：Git 提交存在、当前工作树内容和正在运行的页面是三件不同的事。交接时除提交哈希外，还要报告当前分支、上游、
工作区状态以及运行服务读取的目录，不能仅凭浏览器页面判断代码是否丢失。

## 四、已有积木与新造轮子

复用：受保护路由外壳、统一 HTTP Client、ApiError、文档分页 API、设计令牌、PageHeader、Vitest 与 Vue Test Utils。

新增：EmbeddingJob entity、最近任务发现与任务操作 API 适配、批量逐项校验、向量工作区 composable、独立页面 UI、
批量状态恢复和集中轮询；检索侧增加多关键词 DTO、标签输入、URL 状态与多词高亮；问答侧增加 GroundedAnswer entity、
API 运行时校验、单次请求 composable、来源与用量 UI。

没有新增第三方依赖，也没有修改后端、文档库状态机或 Pinia Auth Store；只把共享范围选择器的关键词专用文案泛化为检索/问答文案。
