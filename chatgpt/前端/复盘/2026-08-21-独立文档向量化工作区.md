# 2026-08-21 学习与架构复盘：独立文档向量化工作区

## 一、今天解决了什么

今天把后端已经存在的向量任务能力变成了一个独立、可操作的前端页面。用户可以选择单篇或多篇文档创建向量任务，
看到等待文档、排队、处理中、成功、失败和取消状态，并取消尚未被 Worker 领取的任务。

## 二、完整数据流

```text
EmbeddingsPage
  → EmbeddingWorkspacePanel：筛选、选择和状态展示
  → useEmbeddingWorkspace：批量编排、逐项结果、集中轮询和取消
  → embedding-api：HTTP 状态与 unknown DTO 运行时校验
  → Go API：保存任务意图、查询或取消任务
  → PostgreSQL embedding_jobs：任务状态真相
  → Embedding Worker：调用模型并原子保存向量与成功状态
```

文档库只提供已有 `listDocuments` API 积木。向量模块没有修改 `DocumentLibraryPanel` 或上传队列，页面路由负责把两个
能力放在同一应用中，因此“文档管理”和“向量任务生命周期”可以分别演进和测试。

## 三、关键架构认识

### 1. TypeScript 类型不能代替 HTTP 运行时校验

Axios 泛型只能表达开发时预期，不能证明真实后端响应正确。向量 API 先以 `unknown` 接收，再核对六种状态、整数、时间、
可空 Token 字段和批量逐项结构。单篇响应还必须属于请求的 document ID，批量响应必须为每个请求 ID 返回且只返回一次。

### 2. 前端提交意图，不调度模型

浏览器只调用创建任务接口。排队顺序、并发、重试和远程模型调用属于后端 Worker；前端最多 4 路并发查询只是读取状态，
不能与后端 Worker 并发配置绑定。

### 3. 一个调度器优于每行一个定时器

如果每个文档行都建立 `setInterval`，100 个活动任务会产生 100 套独立节奏、重叠请求和复杂清理。当前 composable 使用一个
递归调度器，分组执行最多 4 路查询；没有活动任务就停止，页面隐藏就暂停，恢复可见后立即同步。

### 4. “没有信息”不能伪装成业务事实

后端目前只能按 job ID 查询，没有按 document 找最新任务或列出任务的接口。因此页面无法永久证明某文档“从未向量化”。
当前 Session Storage 只恢复本浏览器会话知道的 job ID，界面明确写“未跟踪不等于从未向量化”。OwnerScope 仍由后端保证。
由于后端只复用活动任务，未知的历史 succeeded 文档可能在再次提交后重新生成；页面因此在真正提交前明确提示远程模型额度风险。

### 5. 解析 ready 与向量 succeeded 是两件事

文档 `ready` 表示 chunks 可用；只有向量任务 `succeeded` 才表示本轮模型向量已经生成。前端分别展示两套状态，不能因为
文档可关键词检索就直接声称它可语义检索。

## 四、已有积木与新造轮子

复用：受保护路由外壳、统一 HTTP Client、ApiError、文档分页 API、设计令牌、PageHeader、Vitest 与 Vue Test Utils。

新增：EmbeddingJob entity、四个正式 API 适配、批量逐项校验、向量工作区 composable、独立页面 UI、会话恢复和集中轮询。

没有新增第三方依赖，也没有修改后端、文档库业务组件或 Pinia Auth Store。

## 五、测试与浏览器检查带来的认识

- API 测试覆盖合法 DTO、未知状态、批量混合结果、文档/任务 ID 串行和缺失逐项结果；
- composable 测试覆盖单篇轮询成功、批量部分失败和刷新恢复后取消；
- 组件测试覆盖选择、提交、任务展示和筛选空态；
- 真实登录态空文档页面检查验证路由、导航、空态和 Session 提示，无控制台错误；
- 首次截图发现侧栏压缩后操作栏布局过密，改为稳定两行布局后核对页面宽度与滚动宽度一致。

## 六、仍需完成

3. 后端提供按 document 查询最新任务或任务列表接口；

5. 后续由页面层把批量上传成功 IDs 传给向量模块，不合并两个 feature 状态机。
